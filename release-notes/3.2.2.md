## Apply sets REAPER up properly on a fresh machine

On a machine that had never been set up, pressing Apply left REAPER reopening
the last project at startup instead of starting a new one.

3.2.0 changed the Preferences checkboxes to open showing whatever REAPER
already had, rather than the recommended setup. On a fresh install REAPER's own
default is "reopen the last project", so the startup box opened unticked — and
because Apply now sets each option both ways, Apply wrote that default straight
back. The same went for prompt-to-save and the peaks subfolder.

They open ticked again, because setting REAPER up the standard way is what the
app is for. Unticking one still genuinely turns it off. **Record-arm new
tracks** is the exception: it's a personal choice rather than part of the
standard setup, so it still opens on whatever REAPER has — off on a fresh
install, and left on for anyone who turned it on.

## Audio lands in Audio/ whatever template REAPER is using

On the same machine the peaks nested but the audio didn't, recording straight
into the project folder.

A project template carries its own media path, and it overrides the preference.
Apply sets the template's media path to match — but only for the template
picked in the dropdown, and the dropdown recognised a template only if it lived
in `ProjectTemplates` and its name matched loosely. A template REAPER was
already using that the dropdown didn't recognise showed as "(none)", stayed in
use, and was never touched, so its empty media path won.

Apply now reads back which template REAPER will actually open and aligns that
one, wherever it lives. The dropdown shows it too, instead of "(none)", and
matches it exactly — "Show.RPP" no longer mistakes itself for "My Show.RPP".

## Apply double-checks everything, every time

Apply used to skip a setting when it already looked right, and then report
what it had meant to do. Both of those trusted a single read of `reaper.ini`
that could itself be wrong. Now:

- **Every setting is written on every Apply**, whether or not it looked
  correct already. Nothing is skipped on the strength of a read.
- **The template is aligned on every Apply** — whichever one REAPER will open,
  however it came to be set.
- **Everything is read back off disk afterwards**, and the report lists each
  setting with ✓ or ✗ against what is actually there, not what was intended.
  If anything did not hold, the dialog says so and says why.
- **A setting that appears twice** in `reaper.ini` is collapsed to the one
  value written. Before, the first copy was updated and read back as proof,
  while REAPER could be reading the other.
- **Apply refuses while REAPER is running.** REAPER keeps its preferences in
  memory and writes them all back when it quits, which silently undoes
  anything written meanwhile — the most likely reason a setting "doesn't
  stick". This was only checked when SiRPS opened, so launching REAPER
  afterwards went unnoticed.
