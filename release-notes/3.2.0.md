## Four preferences that never actually worked

Every setting in the Preferences tab wrote a key and reported success. Three of
them were writing the wrong key, so REAPER was never told what you asked for —
and one of the three set the opposite of what its checkbox promised.

**Peak files.** The `peaks/` subfolder option wrote `peakcachegenmode`, which
controls only *when* peaks are generated — on import, and on project load. Peak
*location* is `altpeaks &4`. Worse, `peakcachegenmode` defaults to `3`, and the
code ORed bit 1 into it: `3 | 1` is `3`, so the write was a no-op even on its own
terms. This is the one that left `.reapeaks` sitting beside the audio.

**Startup behaviour.** `loadlastproj` is an enum, not a bitfield — 19 is "new
project", 16 is "last active project". The code masked it (`& ~1 & ~2`), which
turns 19 into 16. Ticking "open a new project on startup" set REAPER to reopen
the last project instead.

**Prompt to save on new project.** Wrote `saveopts &1`, which is "when
overwriting a project file, rename the old one to .rpp-bak". The real key is
`newprojdo &1`. An unrelated setting was toggled instead.

**Choosing a template** also wrote `newprojdo=1`, apparently as a "use the
template" flag. There is no such flag — setting `newprojtmpl` is what makes
REAPER use it — and `newprojdo` is the prompt-to-save bitfield, so picking a
template quietly rewrote an unrelated preference.

All four now write the documented key, and the media path and save path, which
were already correct, are unchanged.

## Record-arm new tracks

A new checkbox: new tracks arrive record-armed. It sets `deftrackrecflags &1`,
bit 1 only — the same field carries the record-config dropdown in bits 16 to
128, which survive untouched.

## Checkboxes tell the truth now

The four checkboxes were hardcoded to start ticked and could only ever switch a
setting on, so unticking one did nothing while looking like it meant something.
They now open reflecting what REAPER actually has, and toggle it either way.
